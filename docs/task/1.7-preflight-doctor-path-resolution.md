## 🎯 Purpose & Scope

Provide a robust, monorepo-aware package resolution utility that the CLI Doctor (task 1.13) uses to locate the consumer's installed `@devcabs/folio-engine` and their own `package.json` — without relying on `process.cwd()` assumptions that break in Turborepo, Nx, or pnpm workspace environments. All file system operations must degrade gracefully (never throw) so the doctor can produce meaningful user feedback even in hostile or unusual project layouts.

---

## 🔍 Problem Statement

`src/diagnostics/migrationDoctor.ts` (task 1.13) will inspect the consumer's installed `@devcabs/folio-engine` version. Naive implementations do `JSON.parse(fs.readFileSync('./package.json'))` or walk relative paths from `process.cwd()`. In monorepos (Turborepo, Nx, pnpm workspaces), `process.cwd()` may be the workspace root, not the package root. The installed engine version may live in a nested `node_modules` or be hoisted. This produces wrong version comparisons or silent failures.

---

## 📄 Key Files to Create / Modify

1. **`src/diagnostics/packageResolver.ts`** *(New)*
   - `resolveInstalledEngineVersion(): { version: string; pkgPath: string } | null`
     - Primary strategy: `require.resolve('@devcabs/folio-engine/package.json', { paths: [process.cwd()] })` — finds the actual installed package.json regardless of hoisting.
     - Fallback for ESM contexts: `import.meta.resolve('@devcabs/folio-engine/package.json')` (guard with `typeof import.meta !== 'undefined'`).
     - Reads and parses the resolved `package.json`, extracts `version`.
     - Returns `null` on ANY error (module not found, parse failure, missing `version` field) — never throws.
   - `resolveConsumerPackageJson(): { version: string; name: string; path: string } | null`
     - Starts at `process.cwd()`.
     - Walks UP the directory tree looking for a `package.json` where `name !== '@devcabs/folio-engine'`.
     - Stops at the git root (detected by presence of `.git` directory) or filesystem root (`/`).
     - Returns `null` if no suitable `package.json` is found.
     - Never throws — wraps all `fs` calls in `try/catch`.
   - `resolveContentFiles(consumerRoot: string): string[]`
     - Checks for known consumer content files in common locations:
       - `{consumerRoot}/sample-nodes.json`
       - `{consumerRoot}/src/engine-setup.ts`
       - `{consumerRoot}/engine-setup.ts`
       - `{consumerRoot}/src/folio/engine-setup.ts`
     - Uses `fs.existsSync` for each path.
     - Returns only the paths that actually exist.
     - Never throws.

2. **`src/diagnostics/migrationDoctor.ts`** *(Pre-wire for 1.13)*
   - Import and use `resolveInstalledEngineVersion()` and `resolveConsumerPackageJson()` for all version lookups.
   - Zero direct `fs.readFileSync('./package.json')` calls at the top level or hardcoded relative paths.
   - Null handling:
     - If `resolveInstalledEngineVersion()` returns `null`, print:
       ```
       ⚠️  Could not resolve @devcabs/folio-engine installation.
       Run from within a project that has @devcabs/folio-engine installed.
       ```
       Then exit with code `0` (not `1` — this is a configuration issue, not a script error).
     - If `resolveConsumerPackageJson()` returns `null`, print a warning but continue with reduced diagnostics.
